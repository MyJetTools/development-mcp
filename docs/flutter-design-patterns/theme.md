# Theme and layout — the web client's look, on a phone

The phone app is the same product as the Dioxus client, drawn by Flutter instead of the browser.
The phone rules of a Dioxus phone surface (an app bar, a floating tab bar, bottom sheets, 44 px
targets, safe areas, no hover, one scroll per screen) hold as they are; this is how each of them is
written in Flutter. The CSS side is §15 of `get_dioxus_design_patterns`; this is its twin.

## 1) Tokens — generated from the Dioxus client's CSS

The web's vocabulary is its tokens file (in the MT terminal, `mt-client-mobile/css/01-tokens.css`):
the shared palette (`--bg-primary`, `--accent-color`, …) and the phone roles (`--appbar-*`,
`--tabbar-*`, `--sheet-*`, `--tap-min`, …), dark under `:root` and light under
`[data-theme="light"]`. **The app does not get a palette of its own: it gets that file, generated
into Dart.**

```
css/01-tokens.css (the Dioxus client) ──tool/gen_tokens.dart──▶ lib/theme/tokens.g.dart
```

```dart
// lib/theme/tokens.g.dart
// GENERATED by tool/gen_tokens.dart from the Dioxus client's css/01-tokens.css — do not edit
@immutable
class MTokens extends ThemeExtension<MTokens> {
  const MTokens({
    required this.bgPrimary,
    required this.bgSecondary,
    required this.accentColor,
    required this.tapMin,
    required this.appbarH,
    required this.tabbarH,
    required this.sheetRadius,
    // … every token the CSS declares, under the same name in camelCase
  });

  final Color bgPrimary;
  final Color bgSecondary;
  final Color accentColor;
  final double tapMin;
  final double appbarH;
  final double tabbarH;
  final double sheetRadius;

  static const dark = MTokens(bgPrimary: Color(0xFF17232E) /* … */);
  static const light = MTokens(bgPrimary: Color(0xFFF5F7FA) /* … */);

  // copyWith / lerp — generated too
}

extension MTokensOfContext on BuildContext {
  MTokens get tokens => Theme.of(this).extension<MTokens>()!;
}
```

```dart
// ✅ CORRECT
Container(color: context.tokens.bgSecondary)

// ❌ WRONG — a colour spelled in Dart: the web and the app go one way, this widget another
Container(color: const Color(0xFF1E2C39))
```

What the generator does with each kind of value:

| In the CSS | In Dart |
|---|---|
| `#rrggbb`, `#rrggbbaa`, `rgba(…)`, `rgb(r g b / a%)` | `Color` |
| `var(--other)` | resolved to the other token's value — light and dark alike |
| `Npx` | `double`, logical pixels |
| font stacks | the first family, which is bundled (section 6) |
| `env(safe-area-inset-*)`, a keyboard inset | not generated — Flutter reports them (`MediaQuery`, sections 3 and 5) |
| shadows with `inset` | not generated — `BoxShadow` has no inset; a raised-button recipe of its own in `lib/theme/`, built from the generated colours |

- **`tokens.g.dart` is never edited.** A colour changes in the CSS, and both surfaces change with
  it. `test/tokens_are_current_test.dart` runs the generator in memory and fails when the committed
  file differs — the twin of `build.rs` compiling the CSS on every build.
- **The undeclared-token guard comes free.** A web `build.rs` refuses a `var(--x)` no rule
  declares, because CSS fails silently; in Dart `context.tokens.x` for an undeclared `x` does not
  compile.

## 2) The theme

- **The choice is the core's, resolving it is Flutter's.** The stored setting is `"dark"`,
  `"light"` or nothing; nothing means the OS decides — `MediaQuery.platformBrightnessOf(context)`.
- **`ThemeData` is built from the tokens**, once per brightness, with `MTokens.dark` /
  `MTokens.light` as its extension; widgets read `context.tokens`.
- **The status bar follows the theme** — on the web that is `<meta name="theme-color">`; here it is
  `AnnotatedRegion<SystemUiOverlayStyle>` at the root, with the icon brightness of the theme.
  Android draws edge-to-edge by default (since Flutter 3.27): the app's own background is under the
  bars, so only the icons' brightness is set.
- **Material widgets come from `package:material_ui/material_ui.dart`** — Material left the SDK in
  Flutter 3.47.

## 3) Safe areas

`env(safe-area-inset-*)` is `MediaQuery.paddingOf(context)`:

```dart
// the app bar: its own height plus the notch
final top = MediaQuery.paddingOf(context).top;
SizedBox(height: context.tokens.appbarH + top, child: …)

// a floating tab bar sits above the home indicator
final bottom = MediaQuery.paddingOf(context).bottom;
Positioned(left: …, right: …, bottom: bottom + context.tokens.gapMd, child: const MTabBar())
```

- Never a hardcoded inset — the same rule as `env()` over numbers.
- Pre-auth screens wrap their body in `SafeArea`.
- A phone layout is portrait: Info.plist (`UISupportedInterfaceOrientations`) and the Android
  activity (`screenOrientation`) say so — a landscape phone layout is a design, not a reflow.

## 4) Touch — targets, pressed, no hover

- **`tokens.tapMin` (44) is the floor** for anything tappable. A mis-tap in a trading app costs
  money.
- **Opposite actions are never side by side** — Buy and Sell at opposite ends with the size between
  them, each labelled with the price it fills at.
- **No hover.** No `MouseRegion` UI. Feedback is the pressed state (`:active` on the web): a raised
  button moves into the surface while it is held — `GestureDetector.onTapDown / onTapUp /
  onTapCancel`, or an `InkWell` with the tokens' colours.

## 5) One scroll per screen

The web's rule: the body fills the screen and does not scroll; exactly one element inside a screen
does. In Flutter that one element is the `Expanded` child of the screen's `Column`:

```dart
// ✅ CORRECT — the header and the price block stay, the list scrolls
Column(
  children: [
    const RenderInstrumentHeader(),
    const RenderPriceBlock(),
    Expanded(child: ListView(children: rows)),
  ],
)
```

```dart
// ❌ WRONG — a ListView in a Column with nothing to bound it:
// "Vertical viewport was given unbounded height" — the twin of the web's missing `min-height: 0`
Column(children: [const RenderInstrumentHeader(), ListView(children: rows)])
```

- **`Expanded` is what `min-height: 0` was** — it gives the scrollable a height to scroll within.
  One per screen; a second vertical scrollable inside it is a page that cannot decide which one the
  thumb meant.
- **Centred content that can outgrow its box** (a sign-in card under the keyboard) is centred
  inside a scroll view, so it loses nothing from its top — the web's `margin: auto` rule
  (`get_flutter_client_bootstrap_guide`, topic `templates-and-dialogs`).
- **The keyboard** is `MediaQuery.viewInsetsOf(context).bottom`. Screens with fields keep
  `Scaffold(resizeToAvoidBottomInset: true)`.

## 6) Fonts

- **Bundled** — the first faces of the web's font stacks, in `assets/fonts/`, declared in
  `pubspec.yaml`. A system fallback would make the app read differently from the web.
- **Prices use tabular figures** (`FontFeature.tabularFigures()` where the face is not monospaced),
  so a price that ticks does not shift its neighbours.

## 7) Sheets

On a phone a modal is a bottom sheet. *What* is open lives in `AppState` (`DialogState`, §9);
*how* it appears is the shell's sheet host:

- **The drag is the framework's.** Material's `BottomSheet` widget does the grip and the
  drag-to-close and calls `onClosing`; the host animates it in and out with an
  `AnimationController`. Thresholds tuned for a browser that has no sheet of its own are not
  ported.
- **The grip drags, the body scrolls** — a `ListView` inside the sheet, never the sheet itself
  scrolling: one element that does both guesses wrong exactly when the content is long.
- **The backdrop closes it** (`ModalBarrier` coloured with the sheet-backdrop token), and so does
  Android's back — a `PopScope` at the shell closes the open sheet before anything else pops.
- No close cross: a swipe, a tap outside, or back.

## 8) Haptics — the phone's own

The browser has none; the app uses them sparingly:

| Moment | Call |
|---|---|
| a tab, a timeframe, a chip switched | `HapticFeedback.selectionClick()` |
| an order accepted | `HapticFeedback.mediumImpact()` |
| an order refused | `HapticFeedback.heavyImpact()` — and the reason inline, on screen |

A vibration never replaces what the screen says.

## 9) What may differ from the web, and what may not

| May differ — the platform's | May not — the product's |
|---|---|
| how a sheet slides and is dragged | the tokens: colours, sizes, radii |
| Android's back, iOS's swipe-back | the words |
| haptics | every number and how it is formatted |
| scroll physics (iOS bounce) | the tabs, their order, what each one shows |
| the status bar and the keyboard handling | what each control does |
| the app icon and the splash | what is stored, under which key, in which shape |

A difference in the right column is a bug on one of the two surfaces — find which, fix it there,
and if the fix is logic, it goes into the core.
