## Release Guide — How to deploy services

### Single-repo (one service = one GitHub repo)

Create a GitHub release — tag and title are the version number:

```bash
gh release create 0.1.0 --title "0.1.0" --notes ""
```

The workflow triggers on any tag (`tags: "*"`), builds the service, and pushes the Docker image.

---

### Monorepo (multiple services in one GitHub repo)

Each service has its own tag pattern: `{service-name}-{version}`.

#### Create a release

```bash
gh release create {service-name}-{version} --title "{service-name}-{version}" --notes ""
```

Example:
```bash
gh release create price-feed-binance-0.1.0 --title "price-feed-binance-0.1.0" --notes ""
```

This creates both the GitHub release and the tag. The workflow file `release-{service-name}.yaml` triggers on tags matching `{service-name}-*` and builds only that service.

#### Check build status

```bash
# List recent runs
gh run list --limit 5

# Watch a specific run
gh run watch {run-id}

# View logs of a failed run
gh run view {run-id} --log-failed
```

#### Re-deploy the same version

Delete the release + tag, then create again:

```bash
gh release delete {service-name}-{version} --yes --cleanup-tag
gh release create {service-name}-{version} --title "{service-name}-{version}" --notes ""
```

### Prerequisites

**Single-repo.** `Dockerfile` and `.github/workflows/release.yaml` are generated by `ci-utils` from
`build.rs` — run `cargo build` once and commit both. Nothing else to do.

**Monorepo.** These must be committed and pushed before the first release:

1. **Dockerfile** — the runtime one, in the service directory (`{service-dir}/Dockerfile`)
2. **Release workflow** — `.github/workflows/release-{service-name}.yaml`
3. **Builder-image workflow** — `.github/workflows/build-{service-name}-docker.yaml`, and it has
   been run once by hand (`workflow_dispatch`) so `{service-name}-build-docker:latest` exists
4. **`Cargo.lock`** — un-ignored per service in `.gitignore` and committed

If the workflow file is not in the repo at the time the tag is created, GitHub will not trigger the build.

Without 3 and 4 the release still succeeds — it just falls back to the cold build and takes ~10
minutes instead of ~2. The full pattern, including both workflow files verbatim, is in the
app-bootstrap guide, topic `ci-monorepo` (`get_app_bootstrap_guide` with `topic`) — generate them
from there, do not improvise.

### Re-baking the builder image (monorepo)

Re-run `build-{service-name}-docker.yaml` by hand whenever the dependency graph moves — a
MyJetTools tag bumped, a dependency added, `Cargo.lock` updated. Nothing else triggers it, and it
takes ~10 minutes. Skipping it does not break a release; the release just recompiles more than it
needed to.

After a release, confirm in the run that *Build (warm, in the builder image)* executed and the cold
steps were skipped. If the cold steps ran, the pull failed — check that the image exists and that
`PUBLISH_TOKEN` can read it.

Dioxus WASM services (`dx build`) do not use the builder image at all — they build inside the
`ghcr.io/my-jet-tools/dioxus-docker` container instead. See the Dioxus client-side bootstrap guide.

### Dioxus — the production release ships an optimised `.wasm`

**Every production release of a Dioxus project** — a client-side app, or the web half of a
fullstack app — goes through this step before `gh release create`. Fetch the WASM optimization
guide (`get_wasm_optimization_guide`) and check the project against its checklist:

1. Every release `dx build` / `dx bundle` — the local build script and the CI workflow — has
   `--debug-symbols false`. Without it the bundle keeps its debug info: +38% of the module.
2. `Cargo.toml` has `[profile.wasm-release]` with `opt-level = "z"`, `lto = true`,
   `codegen-units = 1`. Settings for the bundle in `[profile.release]` do not count — dx builds the
   web bundle under `wasm-release`.
3. No `strip` and no `panic = "abort"` in any profile.
4. The build fails when wasm-opt fails: `grep "wasm-opt failed"` over the `dx build` output — dx
   itself succeeds and ships the bundle unoptimised.

A project that does not pass is fixed first, and the fix is released — never a release that
knowingly ships an unoptimised bundle.

After the run: the build log has no `wasm-opt failed` line. A local release build prints the size
of the `.wasm` and of its gzip; compare them with the bundle it replaces.

A single-repo fullstack service builds with the workflow `ci-utils` generates, which runs
`dx bundle` without `--debug-symbols false` (known gap of `ci-utils` 0.1.3). Do not hand-edit the
generated file — tell the user that the released bundle keeps its debug info until `ci-utils` is
fixed.

### Version extraction

The workflow extracts the version from the tag by stripping the `{service-name}-` prefix:

```yaml
TAG="${{ github.ref_name }}"          # e.g. margin-engine-0.2.1
VERSION="${TAG##*-}"                   # e.g. 0.2.1
```

This version is used for:
- Updating `version` in `Cargo.toml` during build
- Tagging the Docker image: `ghcr.io/{org}/{service-name}:{version}`
